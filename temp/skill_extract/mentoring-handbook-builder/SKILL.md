# 带教手册生成器

把录音转写文字变成一份能让"中上水平的带教者带到及格线"的带教手册。核心分工原则：**能靠脚本机械完成的步骤（清洗统计、排版生成）交给脚本，需要理解内容、做判断的步骤（提炼经验、组织结构、拿捏详略）留给你自己来做**，不要用脚本或者僵化的模板替代这部分判断，也不要凭空脑补内容——手册的价值就来自转写文字里专家的真实经验。

## 整体流程

**第一步：预处理转写文字（脚本，机械执行）**

```bash
python scripts/preprocess_transcript.py <转写文字.txt> -o <输出.json>
```

这一步只做清洗、说话人切分、阶段识别、字数统计，不做内容判断。运行完看终端摘要：总字数是否足够支撑2-3万字的手册（经验上原始转写素材至少需要8000字以上信息密度较高的内容）、各阶段/说话人字数分布是否合理。如果明显偏少，如实告知用户素材可能不够，建议补充访谈，而不是靠自己编内容凑数。

**第二步：通读转写文字，确认三个定位信息**

从转写文字（或用户提供的信息）里找到：具体行业岗位、这份手册面向的带教者水平、要解决的具体问题。这三点决定了你写作时的详略取舍，缺一个都问用户要，不要自己瞎猜。

**第三步：撰写手册正文（你自己判断，不要套用僵化模板）**

依次阅读这三份参考文档，再动笔：

- `references/内容标准.md` —— 必含模块、禁止内容、验收标准、"国际顶尖标准"的具体定义
- `references/手册结构模板.md` —— 章节骨架（不是逐字模板，章节数量和篇幅要按内容实际情况调整）
- `references/写作风格指南.md` —— 怎么避免AI味、保持案例的真实感和现场感

写作时的核心判断题一直是同一个：**这一段内容，换一个中上水平的带教者拿去带人，带得到及格线吗？** 判断点、案例、纠偏语要优先从转写文字里提炼，不要脱离素材编造；如果某个模块转写文字里内容确实单薄，如实反映详略，别注水。

正文必须按照下面的markdown书写约定来写（`build_docx.js` 依赖这套约定生成排版，写错了脚本认不出结构）：

```
---
title: [手册标题]
subtitle: [副标题，可选]
position: [适用岗位/课题]
author: [默认罗宏伟，除非用户另有指定]
date: [年-月]
---
# 一级标题 → 章
## 二级标题 → 节
### 三级标题 → 小节（如"关键判断点与引导提问"）
> 以 > 开头的行 → 案例内容，会渲染成浅灰底纹色块，建议案例开头写"【案例】"
→ 以 → 开头的行 → 引导提问/纠偏语，会渲染成楷体强调
- 以 - 开头的行 → 项目符号列表
其他文字 → 正文段落
```

**第四步：篇幅与结构自检（脚本，机械执行）**

```bash
python scripts/check_length.py <手册草稿.md>
```

看总字数是否在20000-30000区间、有没有章节明显偏薄。偏薄不一定要硬加内容——先回去看是不是转写文字里这块本来就没深挖到，如果是，在附录"待补充清单"里如实注明，不要靠正确废话注水凑字数。

**第五步：生成最终Word文档（脚本，机械执行）**

```bash
node scripts/build_docx.js <手册草稿.md> <输出.docx>
```

会自动套用 `references/word排版规范.md` 定义的封面、目录、标题样式、页眉页脚、案例底纹等格式，具体参数在 `assets/word_style_config.json`，正常情况不需要改。

**第六步：渲染检查**

```bash
python /mnt/skills/public/docx/scripts/office/soffice.py --headless --convert-to pdf <输出.docx>
pdftoppm -jpeg -r 100 <输出>.pdf page
```

把生成的图片过一遍，确认封面、目录、章节样式、案例底纹显示正常，再交付给用户。目录页在Word里打开后需要按F9或右键"更新域"才会显示正确页码，这是Word域机制决定的，交付时提醒用户一句。

## 什么时候可以跳过第一步脚本

如果用户直接给的就是已经整理好、带明确说话人和阶段标记的干净文字，第一步的清洗意义不大，但字数统计仍然有用，建议照样跑一遍，成本很低。

## 什么时候需要停下来问用户

转写文字总字数明显不足以支撑2-3万字手册时；第二部分"三个定位信息"缺失且无法从上下文合理推断时；转写文字里的内容跟实际操作规程明显冲突、涉及安全风险，你不确定该不该收录时——这几种情况下，问用户，不要自己替用户做决定。
